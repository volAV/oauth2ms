* Overview
This tool can be used to fetch oauth2 tokens from the microsoft identity endpoint.
Additionally, it can encode the token in the [[https://docs.microsoft.com/en-us/exchange/client-developer/legacy-protocols/how-to-authenticate-an-imap-pop-smtp-application-by-using-oauth#sasl-xoauth2][XOAUTH2 format]] to be used as authentication in IMAP mail servers.
Example configuration for emacs given in [[steps.org]].

* Dependencies
Requires mbsync >= 1.3.
More information available at: https://github.com/harishkrupo/oauth2ms/issues/2#issuecomment-846464452
This implementation requires Python >= 3.14, GnuPG, and a POSIX system with
=fcntl.flock= support. UV manages development; UV or pipx can install the application.
Python dependencies are declared in =pyproject.toml= and locked in =uv.lock=.
MSAL >= 1.26.0 is required for the validated OAuth flow.

* Installation
Install UV using its [[https://docs.astral.sh/uv/getting-started/installation/][official instructions]], then from this checkout:
#+begin_src sh
  uv sync --locked
  uv run --locked oauth2ms --help
#+end_src
UV creates the project environment in =.venv=. The checked-in =.python-version=
selects Python 3.14, while the package supports Python 3.14 and newer.

For mail clients and systemd, install the package as an isolated UV tool:
#+begin_src sh
  uv python install 3.14
  uv tool install --python 3.14 .
#+end_src
Alternatively, install with pipx using the managed Python interpreter:
#+begin_src sh
  pipx install --python "$(uv python find 3.14)" .
#+end_src
Both installers isolate the application from the system Python. Provision Python
3.14 first; the operating system's interpreter does not need to be upgraded.

Ensure the selected installer's binary directory (normally =~/.local/bin=) is in the session
and systemd PATH. If an older standalone =oauth2ms= exists there, back it up and
move it aside first; do not overwrite it implicitly with =--force=. GnuPG must
be installed separately and remain available in PATH. The packaged command keeps
the same options and config/cache paths; do not copy individual source files.
Application development dependencies stay in the project environment, not the
installed tool environment.

=uv tool install= resolves its own runtime environment rather than consuming the
project lock. For an exact locked deployment, run =uv sync --locked --no-dev= in a
stable checkout and point mail clients at its absolute =.venv/bin/oauth2ms= path.
Do not move the checkout or its virtual environment after configuring that path.

** XDG CONFIG HOME
   For the app to locate your config file, the =$XDG_CONFIG_HOME= environment variable must be set.
   It is generally set to =$HOME/.config=.

* Usage
Create a config file with the below details at =$XDG_CONFIG_HOME/oauth2ms/config.json=
#+begin_src json
  {
      "tenant_id": "TENANT_ID",
      "client_id": "CLIENT_ID",
      "client_secret": "CLIENT_SECRET",
      "redirect_host": "localhost",
      "redirect_port": "5000",
      "redirect_path": "/getToken/",
      "scopes": ["https://outlook.office.com/IMAP.AccessAsUser.All"]
  }
#+end_src
If you aren't sure how to fetch the the TENANT_ID, CLIENT_ID and CLIENT_SECRET values, read more on [[file:steps.org][steps.org]].
After creating the config file, execute =oauth2ms=, it should pop up a browser window asking you to login.
Once logged it, it should redirect you to a page which says "Authorization complete.". On the terminal you should
see the token printed. Subsequent fetches should use the refresh token to get the access token. Call =oauth2ms= with
the ~--encode-xoauth2~ to get the token in [[https://docs.microsoft.com/en-us/exchange/client-developer/legacy-protocols/how-to-authenticate-an-imap-pop-smtp-application-by-using-oauth#sasl-xoauth2][XOAUTH2 format]].
#+begin_src sh
  oauth2ms --encode-xoauth2
#+end_src
Optionally, you can add "https://outlook.office.com/SMTP.Send"
to the list of scopes to use the token for stmp. See [[steps.org]] for information on configuring emacs for sending mail
via smtp with xoauth2.

** Encryption
Encryption of the fetched token cache can be enabled using the =-e= (=--encrypt-using-fingerprint=) option. The option takes the
email/fingerprint to identify the gpg key to use for encrypting and decrypting the token cache.
#+begin_src sh
  oauth2ms -e <gpg recipient fingerprint>
#+end_src

** Credential safety
Use =-e= on every invocation that reads or updates an encrypted cache. An empty
recipient is rejected rather than silently switching to plaintext mode. Without
=-e=, the cache still contains plaintext credentials: keep it private.

The bootstrap file =$XDG_CONFIG_HOME/oauth2ms/config.json= must be plaintext JSON.
Create it outside source control with owner-only permissions. Do not put client
secrets, token caches, private keys, or their backups in Git. The cache includes a
copy of the configuration and its client secret. Once an encrypted cache has been
verified, remove the plaintext bootstrap file or keep only an encrypted backup.
An encrypted cache needs the corresponding private key and an unlocked GPG agent.

Encryption and decryption failures exit nonzero without printing a token or
replacing the previous cache. Successful writes use a private temporary file,
=fsync=, and atomic replacement. The cache directory is restricted to mode =0700=;
cache and lock files are restricted to =0600=. Tokens are printed only after a
changed cache has been saved successfully. Diagnostics and the =--no-browser=
authorization URL go to stderr, so stdout remains reserved for tokens.

A persistent =credentials.bin.lock= serializes the entire read/refresh/save cycle,
including interactive authorization, across cooperating oauth2ms processes.
Waiting mail clients can block until authorization or GPG unlocking finishes.
Do not remove the lock file while processes are running, or let an older
unlocked version access the same cache. File locking is intended for a local
filesystem; it does not coordinate caches copied between machines.

The callback accepts only GET requests at the configured redirect path, with one
matching =state= and a single authorization code or error. Unrelated requests do
not complete the flow. MSAL's authorization-code-flow API validates the transaction
and handles PKCE; raw authorization codes and token responses are not logged.
Keep the listener bound to localhost and register the exact redirect URI in Entra.
A trailing slash is removed from =redirect_path= except when it is just =/=.

Changing the client, scopes, or client secret requires a protected reauthorization:
the existing cache contains a configuration snapshot and takes precedence over
the bootstrap file. Stop mail clients, move the old cache to a private location,
then authorize using the updated bootstrap configuration. Never publish terminal
tokens or authorization URLs. Revocation and secret rotation must be performed
in Entra if credentials were exposed; deleting a local file is not revocation.

* Verification
Use the locked project environment for all development checks:
#+begin_src sh
  uv sync --locked
  uv run --locked ruff format --check .
  uv run --locked ruff check .
  uv run --locked ty check
  uv run --locked python -B -m unittest discover -s tests -v
#+end_src
Ruff owns formatting and linting; TY checks both =src/= and =tests/=. Tests use
the standard library's =unittest= runner, so no extra test framework is required.
To apply formatting, run =uv run --locked ruff format .=. To update dependencies
deliberately, run =uv lock --upgrade= and review the lock-file changes before
rerunning these checks. Commit =uv.lock=; do not commit =.venv/= or tool caches.
The tests use disposable GPG keys and synthetic cache data. They cover callback
rejection, real encryption/decryption failures, failed atomic replacement,
token-output suppression, file permissions, and concurrent processes. They do not
contact Microsoft or use personal credentials. Test the browser sign-in and mail
clients separately before replacing a working installation.
